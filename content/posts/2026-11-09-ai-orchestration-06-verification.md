올해 초에는 [Codex에게 밤새 이슈 하나를 맡기고 Draft PR을 받아 봤습니다](/posts/2026-03-26-codex-automation-draft-pr/). 그때는 밀린 버그 몇 개만 정리해 줘도 좋겠다고 생각했는데요.

그러다 가을에는 두 달 동안 새기다의 기능 구현과 테스트까지 대부분 에이전트에게 맡겼고 앱을 세 번 출시했습니다.

새기다(Carve)는 Apple Pencil로 성경을 필사하는 iPad 앱입니다. 혼자 개발하고 있어서 어디까지 맡길지도 제가 정합니다.

회사에서는 AI가 쓴 코드도 거의 한 줄씩 읽지만 새기다에서는 구현 코드를 거의 읽지 않습니다. 대신 작업을 시작하기 전에 범위를 정하고 끝나면 테스트 결과와 실제 앱을 확인하는 데 시간을 씁니다.

자동 검증 덕분에 매번 같은 기준으로 확인할 수 있었지만 테스트를 수천 개 통과하고도 놓친 문제가 있었습니다.

## 무엇을 맡겼나

TestFlight 빌드를 써 보다가 고칠 점이 보이면 먼저 제가 본 현상과 바라는 동작을 적습니다. 에이전트는 코드와 기록을 읽고, 어떤 작업을 함께 진행할 수 있고 어떤 작업을 먼저 끝내야 하는지 정리합니다.

이렇게 작업의 의존관계를 정리한 계획을 Task DAG(Directed Acyclic Graph)라고 부릅니다.

작업을 나누는 방식은 컬리 기술 블로그의 [「AI 에이전트 15개를 동시에 굴리는 법」](https://helloworld.kurly.com/blog/ai-orchestration-2/)을 참고했습니다. 먼저 범위와 검증 기준을 정하고 선행 작업이 필요한 부분과 병렬로 진행할 수 있는 부분을 나누는 방식입니다.

새기다에서는 여기에 작업별 Xcode 빌드 환경과 iPad 시뮬레이터를 붙이고 변경을 합칠 때마다 전체 회귀 테스트를 돌렸습니다.

### 직접 만든 스킬과 맡긴 일

이 흐름을 매번 프롬프트로 설명하다 보니 반복하는 절차를 Claude Code에서 부를 수 있는 스킬로 만들어 뒀습니다. 큰 변경은 계획부터 세우고 출시 전 빌드에서 발견한 자잘한 개선점은 노트에서 바로 분류합니다.

| 스킬 | 맡긴 일 | 남기는 결과 |
| --- | --- | --- |
| `/release-feedback` | TestFlight 개선점 노트를 읽고 결함, 개선, 문구를 분류합니다. 같은 파일을 고칠 항목은 한 묶음으로 만들고, 설계가 필요한 변경은 계획부터 세우게 합니다. | 작업 묶음과 검증 결과를 모은 진행판 |
| `/ios-plan` | 코드와 과거 기록을 먼저 읽고, 거기서 답을 찾을 수 없는 결정만 제게 묻습니다. 작업마다 수정할 파일과 돌릴 테스트, 먼저 끝낼 일을 정합니다. | 제가 읽을 계획 노트와 실행에 쓸 Task DAG JSON |
| `/ios-dag` | 계획을 받아 서로 독립적인 작업을 병렬로 실행합니다. 작업마다 worktree, 빌드 산출물(DerivedData), 시뮬레이터를 분리하고, 범위를 벗어난 변경이 없는지 본 뒤 로컬 통합 브랜치에 모읍니다. | 통합 브랜치와 작업별 실행 기록 |
| `/ios-verify` | 린트, 빌드, 테스트를 돌리고 실행·통과·실패 수를 확인합니다. 개별 작업은 관련 테스트부터, 통합 후에는 전체 회귀 테스트를 돌립니다. | 어디까지 실행됐고 어디서 멈췄는지 보여 주는 검증 결과 |

예를 들어 `/ios-plan`이 만든 계획을 `/ios-dag`에 넘기면 `/ios-dag`는 각 작업을 실행하고 `/ios-verify`의 결과로 다음 묶음을 시작할지 판단합니다. 통합 테스트에서 실패하면 그 자리에서 멈춥니다.

Apple Pencil로 직접 써 보거나 업데이트 후 기록이 남는지 살펴보고, 최종 병합과 출시를 결정하는 일은 제가 맡습니다.

[Worktree와 Local을 비교한 글](/posts/2026-04-02-codex-worktree-vs-local/)에서는 에이전트가 작업할 공간을 나누는 데 초점을 뒀습니다. 작업이 여러 개가 되니 **어떤 변경을 먼저 넣고 합쳐진 결과를 어디에서 확인할지**도 정해야 했습니다.

차트의 날짜 계산을 바꾸면서 자식 리듀서가 현재 시각을 외부에서 받도록 수정했습니다. 부모 리듀서의 테스트도 자식의 날짜 계산을 실행하기 때문에 시각을 함께 넘겨야 했습니다. 먼저 공통 테스트 코드에 시각을 넘기는 부분을 추가한 뒤, 각 작업에서 담당 테스트를 고정된 시각으로 전환했습니다.

새기다의 실행 기록을 2026년 11월 4일까지 집계한 결과는 이렇습니다.

- Task DAG는 21회 실행했고 개별 작업은 217개였습니다.
- 통합 단계의 전체 회귀 테스트는 94회 실행했고 그중 3회가 실패했습니다.
- 말씀 카드 기능은 5단계, 15개 작업으로 진행했습니다. 첫 실행 기록부터 마지막 기록까지 약 3시간이 걸렸으며 이후 검토와 수동 확인 시간은 포함하지 않았습니다.

## 무엇을 확인했나

### 테스트로 기존 동작을 남겨 둡니다

에이전트에게 기능만 만들어 달라고 하면 다음 에이전트는 그 기능을 어디까지 바꿔도 되는지 다시 알아내야 합니다. 그래서 새 기능에는 상태와 동작을 확인하는 리듀서 테스트를, 저장 형식을 바꿀 때는 이전 데이터를 읽는 마이그레이션 테스트를 같이 붙였습니다.

이미 기능별로 모듈과 테스트가 나뉘어 있어서 차트만 바꿨다면 차트 테스트부터 돌릴 수 있었습니다.

검증 스크립트는 테스트가 실제로 실행됐는지, 실패한 테스트가 있는지 확인합니다. 전체 회귀에서는 통과 수가 기준선보다 줄지 않았는지도 봅니다.

![Xcode cloud의 테스트 단계 결과. 조금 더 늘어난 3488개.](/images/tistory/91/02.webp)

*Xcode cloud의 테스트 단계 결과. 조금 더 늘어난 3488개.*

9월 28일에 733개였던 회귀 테스트 통과 수는 11월 4일에 3,446개가 됐습니다. 이미 확인해 둔 동작이 바뀌면 다음 작업에서 바로 알아챌 수 있다는 게 좋았습니다.

다만 전체 테스트는 돌릴 때마다 시간이 들고, 구현과 테스트가 같은 전제를 잘못 이해하면 둘 다 통과할 수 있습니다. 통과 수는 기존 검증이 빠지지 않았는지 보는 신호로 쓰고 그 숫자로 검증의 질까지 판단하지는 않습니다.

### Swift 6.4로 전환하고 동시성 검사를 강화했습니다

동시성 문제는 테스트에서 매번 재현되기 어렵고 변경 내용을 읽어도 놓치기 쉽습니다. 10월 2일에 검증과 출시 빌드를 Xcode 27의 Swift 6.4 컴파일러로 맞췄습니다. 동시성 검사를 경고로 먼저 켰을 때 진단이 355건 나왔고 모듈별로 정리한 뒤 프로젝트 코드의 Swift 언어 모드를 6으로 올렸습니다.

이제 컴파일러가 판단할 수 있는 동시성 문제는 테스트를 실행하기 전에 오류로 드러납니다. 덕분에 에이전트가 자기 구현을 바탕으로 쓴 테스트와는 별개로 확인 기준이 생겼습니다.

그만큼 제품 동작을 바꾸지 않는 전환에도 앱과 테스트 코드를 함께 손봐야 했고, 사용자가 기대한 동작까지 맞는지는 여전히 테스트나 실제 앱에서 봐야 합니다.

### 반복해서 보는 규칙은 린트로 옮겼습니다

리듀서가 현재 시간을 직접 읽으면 같은 테스트도 실행하는 날짜에 따라 결과가 달라질 수 있습니다. 그래서 시각은 밖에서 주입하고 직접 읽는 코드는 SwiftLint에서 오류로 처리합니다. 화면 기능이 SwiftData에 바로 접근하지 않고 저장소를 거치게 하는 규칙도 같은 방식으로 검사합니다.

“이 코드에서는 시간을 이렇게 받는다” 같은 말을 리뷰할 때마다 다시 할 필요가 줄어 좋았습니다. 반면 규칙을 너무 넓게 잡으면 의도와 관계없는 코드까지 막고 그때부터는 예외도 관리해야 합니다.

린트에는 코드에서 분명히 구분할 수 있는 규칙을 두고 저장이나 화면 동작이 사용자 기대에 맞는지는 테스트와 실기기로 확인합니다.

### 저장과 업데이트는 실제 앱으로 확인합니다

필사 화면에서는 PencilKit 캔버스가 펜 입력을 받고 앱은 바뀐 필기를 절 단위로 저장합니다. 저장할 때는 **필사를 시작한 책과 장**을 함께 기억합니다. 저장이 끝나기 전에 다른 필사책을 열어도 방금 쓴 글씨는 원래 책에 남아야 하기 때문입니다.

![](/images/tistory/91/03.webp)

이런 경로는 저장할 때 넘기는 책과 장이 맞는지 테스트로 검사할 수 있습니다. 실제로 펜으로 쓰고 책을 바꾼 뒤, 원래 책을 다시 열었을 때 글씨가 보이는지는 앱에서 확인합니다.

이전 버전을 설치해 기록을 만든 뒤 새 버전으로 덮어 설치하고 업데이트 후에도 필기와 설정이 남는지 봅니다. 이전 버전에서 만든 백업 파일도 복원 테스트에 사용합니다.

필사책 기능은 병렬 구현과 검증에 약 3시간 반, 그 뒤 수동 확인에 약 2시간이 걸렸습니다. 실기기에서 펜으로 써 보고, 앱을 다시 열고, 기록이 남는지 살피는 일은 여전히 제 몫이었습니다.

## 그래도 뭘 놓쳤나

회귀 테스트가 2,200개를 넘었을 때도 **전체 데이터를 지운 뒤 앱을 다시 열면 시작 화면에서 멈추는 문제**가 있었습니다. 2.1.0에도 그대로 나갔고 다른 기능을 손으로 확인하다가 발견했습니다.

새 번역본을 추가할 때는 변환 과정에서 **성경 본문 일부가 빠지는 문제**도 있었습니다. Codex가 변경을 검토한 뒤 원문과 변환 결과를 전부 대조하면서 찾았습니다.

또 한 번은 Xcode를 올린 뒤 기존 설정값이 초기화되는 걸 업데이트 재현 중에 발견해, 심사 대기 중이던 빌드를 바꿔 다시 제출했습니다.

이렇게 해 두니 여러 작업을 맡겨도 어디에서 멈춰야 하는지 기준이 생겼고, 직접 구현할 때보다 더 많은 변경을 시도할 수 있었습니다. 대신 테스트와 규칙을 관리하고 합쳐진 빌드를 실제로 써 보는 일이 늘었습니다.

이제 제 시간은 코드를 한 줄씩 읽기보다 확인할 시나리오를 고르는 데 들어갑니다. 지금도 제일 어려운 건 테스트를 더 돌리는 일이 아니라 **아직 제가 생각해 보지 않은 사용 상황을 찾는 일**입니다.

[다음 글](/posts/2026-11-10-ai-orchestration-07-harness/)에서는 이렇게 코드의 대부분을 맡기고도, 제가 이 앱을 만들었다고 말할 때 무엇을 만들었다는 건지 돌아보려고 합니다.

이 글은 제가 새기다를 개발하며 남긴 기록을 바탕으로, AI의 도움을 받아 초안을 정리하고 문장을 다듬었습니다.
