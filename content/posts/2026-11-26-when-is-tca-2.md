Point-Free 의 블랙프라이데이 할인 메일을 읽다가 「내년에 다룰 것」 목록에 ComposableArchitecture 2.0 이 들어 있는 걸 봤습니다.

![Point-Free 블랙프라이데이 공지 — 내년 계획에 ComposableArchitecture 2.0 이 적혀 있습니다](/images/when-is-tca-2/when-is-tca-2-1.png)

엄밀히는 출시 예고가 아니라 「내년에 다룰 주제」 목록이에요. 그래도 내년에 본격적으로 다룬다니, 기대를 가지고 미리 체크해 보기로 했습니다.

새기다(Carve)는 Apple Pencil 로 성경을 필사하는 앱이고, TCA 로 만들었습니다.

먼저 결론입니다.

- **언제 나오는지는 아직 모릅니다.** 출시일은 발표되지 않았습니다.
- 대신 미리보기 문서를 읽어 보니, **2.0 이 바꾸는 곳이 새기다에서 겪은 문제와 거의 겹쳤습니다.**
- 그래서 올릴 계획입니다. 다만 나오자마자가 아니라 안정된 뒤에, 버전부터 올리고 손대는 화면부터 하나씩 옮기는 점진적 마이그레이션으로 갈 생각입니다.

## 그래서 언제 나오나요

2026-11-26 기준으로 아는 건 이게 전부입니다.

- 2026-03 에 나온 1.25 는 2.0 을 대비한 deprecation 버전입니다. 일부는 바로 경고가 나고, 일부는 SwiftPM trait 을 켜야 납니다.
- 2026-04-01 에 2.0 베타 미리보기가 공개됐습니다. 유료 회원(Point-Free Max) 전용입니다.
- 공개 저장소 최신은 1.26.2(2026-08)이고 2.0 태그는 없습니다.

그래서 「언제」 대신 「무엇이 바뀌는지」를 봤습니다.

## 2.0 에서 바뀌는 것

미리보기 글에서 큰 것만 추렸습니다. 베타를 직접 만져 보진 않았으니 전부 글에 적힌 내용 기준입니다.

| 영역 | 1.x | 2.0 |
|---|---|---|
| Feature 정의 | `@Reducer`, `Reduce { ... return effect }` | `@Feature`, `Update { }` — 동기이고 아무것도 돌려주지 않음 |
| 부수 효과 | `Effect` 를 돌려줌(`.run`, `.send`, `.merge`) | `store.addTask { }`. 작업 안에서 상태를 읽고 `store.modify` 로 씀 |
| 생명 주기 | 뷰의 `onAppear` · `onDisappear` 에서 액션 보내기 | `.onMount` · `.onDismount`. onMount 에서 시작한 작업은 상태가 없어질 때 자동 취소 |
| 부모와 자식 | delegate 액션을 부모가 switch | delegate 클로저, preference, event, trigger |
| 바인딩 | `BindableAction` + `BindingReducer` | `@Bindable` 하나면 됨 |
| 테스트 | `TestStore` 가 `State: Equatable` 을 요구 | 여전히 exhaustive 테스트, Equatable 은 필요 없음 |
| 동시성 | — | Store 가 기본 `@MainActor`. 라이브러리 타입 대부분이 더는 Sendable 이 아님 |

제일 반가운 건 점진적 마이그레이션(incremental migration)을 지원한다는 점입니다. 2.0 패키지에 `ComposableArchitecture1` 모듈이 같이 들어 있어서, `import ComposableArchitecture` 를 그대로 두면 1.x 코드가 컴파일된다고 합니다. 옮기고 싶은 Feature 만 `ComposableArchitecture2` 로 import 를 바꾸면 됩니다. 한 번에 다 갈아엎지 않아도 됩니다.

## 겪은 문제 여섯 가지

새기다를 만들며 TCA 때문에 시간을 쓴 일 여섯 가지를 골랐습니다. 각각 문제, 원인, 2.0 에서의 개선 순서로 적었습니다. 예제 코드는 설명용으로 새로 썼고, 2.0 코드는 미리보기 글을 보고 그린 모양이라 실제 API 와 다를 수 있습니다. 스크린샷은 이 글을 위해 따로 만든 재현용 앱에서 찍었습니다.

### 1. 늦은 onDisappear 경고

**문제**

설정 하위 화면을 닫을 때마다 TCA 가 경고를 냈습니다. 자식 상태는 이미 nil 인데 `ifLet` 에 자식 액션이 도착했다는 내용이었습니다.

```swift
// 1.x — 닫을 때마다 경고가 납니다
SyncStatusView(store: store)
  .onDisappear { store.send(.stopObserving) }
```

재현용 앱에서 시트를 「완료」로 닫으면, Xcode 가 TCA 안쪽에 보라색 runtime warning 을 띄웁니다. 경고 문구는 *received a presentation action when destination state was absent* 입니다.

![시트를 닫은 뒤 ifLet 이 nil 상태에서 액션을 받았다는 Xcode runtime warning](/images/when-is-tca-2/when-is-tca-2-case1-ondisappear.jpg)

**원인**

순서 문제였습니다. 화면을 닫으면 부모 리듀서가 먼저 자식 상태를 nil 로 바꾸고, SwiftUI 는 그 **다음에** `onDisappear` 를 부릅니다. 그래서 정리하려고 보낸 액션이 받을 상태가 없을 때 도착합니다.

지금은 「띄운 화면은 onDisappear 로 액션을 보내지 않는다」를 규칙으로 두고 있습니다. `ifLet` · `@Presents` 로 띄운 화면의 Effect 는 부모가 상태를 치우는 순간 TCA 가 알아서 취소합니다. 뷰 수명에 꼭 묶어야 하는 일만 `.task` 에 묶습니다.

```swift
// 1.x — 뷰가 사라지면 .task 가 취소되고, 그 안의 Effect 도 함께 끝납니다
SyncStatusView(store: store)
  .task { await store.send(.task).finish() }
```

**개선**

2.0 에서는 정리가 화면이 아니라 **상태 수명**을 따라갑니다. `.onMount` 에서 시작한 작업은 상태가 없어질 때 취소되고, `.onDismount` 는 상태가 없어지는 그 순간 불립니다. 늦게 도착할 액션이 애초에 없습니다.

```swift
// 2.0 미리보기를 보고 그린 모양 — 실제 API 와 다를 수 있습니다
var body: some Feature {
  Update { state, action in
    // 상태만 바꿉니다
  }
  .onMount { state in
    store.addTask {
      for await status in syncClient.statusUpdates() {
        try store.modify { $0.status = status }
      }
    }
  }
}
```

다만 상태는 남고 화면만 가려지는 경우는 여전히 뷰의 책임입니다. iPhone 에서 탭을 오갈 때, 화면에 보일 때만 돌아야 하는 광고 갱신 타이머가 여기에 해당합니다. `onDismount` 는 상태가 사라질 때 불리고, 화면이 가려질 때는 불리지 않습니다.

### 2. `Effect?` 헬퍼의 `return .none` 이 nil 이 됨

**문제**

리듀서가 커지면 주제별 헬퍼 함수로 나눴습니다. 헬퍼는 `Effect<Action>?` 를 돌려주고, nil 이면 「내 담당 아님, 다음 헬퍼로」라는 약속이었습니다.

그런데 필사 화면에서 늦게 도착한 조회 결과를 버려야 하는 분기가 조용히 무시됐습니다. 다음 헬퍼가 그 결과를 화면에 합쳐 버렸고, 이 버그는 새기다 2.0 이후 배포된 모든 버전에 들어가 있었습니다.

**원인**

`return .none` 이 nil 로 읽혔습니다. 반환 타입이 `Effect<Action>?` 이면 Swift 는 `.none` 을 TCA 의 `Effect.none` 이 아니라 `Optional.none`, 즉 nil 로 읽습니다. 컴파일러는 아무 경고도 띄우지 않습니다. 그래서 원인을 찾기까지 오래 걸렸습니다.

```swift
func reduceLoading(_ action: Action, state: inout State) -> Effect<Action>? {
  switch action {
  case let .loaded(result):
    guard !state.isClosing else {
      return .none   // 의도: 「처리 끝, Effect 없음」  실제: nil 「내 담당 아님」
    }
    state.content = result
    return .none     // 여기도 nil 이지만, 이미 처리를 마쳐서 결과가 같았습니다
  default:
    return nil
  }
}

// body
if let effect = reduceLoading(action, state: &state) { return effect }
return reduceOther(action, state: &state)   // 버렸어야 할 결과가 여기로 넘어갑니다
```

빌드는 경고 0으로 지나가고, exhaustive 테스트를 돌려야 「바뀌면 안 되는 상태가 바뀌었다」로 드러납니다.

![닫는 중에 도착한 결과를 버려야 하는데 상태가 바뀌어 실패한 테스트](/images/when-is-tca-2/when-is-tca-2-case2-nil.jpg)

고치는 건 한 줄이었습니다. `return Effect<Action>.none` 으로 타입을 적으면 됩니다. 같은 모양이 여섯 군데 더 있었는데, 다행히 거기서는 뒤 분기도 아무것도 하지 않아 결과가 같았습니다.

**개선**

2.0 에서는 `Update` 가 아무것도 돌려주지 않습니다. 「Effect 없음」과 「내 담당 아님」을 같은 단어로 쓸 일 자체가 없으니, 이런 버그는 생길 수가 없습니다. 지금은 규칙으로 막는 걸 2.0 은 구조로 막아 줍니다.

### 3. Effect 의 값 캡처와 응답 액션

**문제**

늦게 도착한 결과를 쓸지 버릴지를 응답 액션에서 다시 판단해야 합니다. 같은 판단이 Effect 를 보내는 곳과 결과를 받는 곳, 두 군데로 흩어집니다. 2번의 「버리는 분기」도 이렇게 생겼습니다.

**원인**

1.x 의 Effect 는 출발할 때 필요한 값을 캡처해 가고, 결과는 응답 액션으로 돌아와야 리듀서가 상태에 쓸 수 있습니다. 캡처한 값은 출발할 때의 값이라, 결과가 늦게 도착하면 「아직 그 장이 열려 있나」를 응답 액션에서 다시 확인해야 합니다. 새기다에는 이런 캡처 리스트가 170곳쯤 있습니다.

```swift
// 1.x
case .refresh:
  return .run { [id = state.chapterID] send in
    let page = try await client.fetch(id)
    await send(.fetched(page))
  }

case let .fetched(page):
  guard page.id == state.chapterID else { return .none }   // 그사이 바뀌었으면 버립니다
  state.page = page
  return .none
```

**개선**

2.0 에서는 작업 안에서 지금 상태를 읽고 `store.modify` 로 바로 씁니다. 응답 액션도, 흩어진 판단도 사라집니다.

```swift
// 2.0 미리보기를 보고 그린 모양
case .refresh:
  store.addTask {
    let id = try store.chapterID
    let page = try await client.fetch(id)
    try store.modify { state in
      guard state.chapterID == id else { return }
      state.page = page
    }
  }
```

### 4. TestStore 가 요구하는 `State: Equatable`

**문제**

빌드 경고를 정리하다가 리듀서를 직접 부르던 테스트(1.x 에서 deprecation 경고를 띄우는 방식)를 `TestStore` 로 옮겼습니다. 그런데 Equatable 이 아닌 State 로 테스트를 만들면 그 줄에서 바로 컴파일 에러가 납니다.

![TestStore 가 State 의 Equatable 을 요구하는 컴파일 에러](/images/when-is-tca-2/when-is-tca-2-case4-equatable.jpg)

**원인**

TestStore 는 `State: Equatable` 을 요구하는데, 몇몇 State 는 Equatable 로 만들기 어려운 값을 들고 있었습니다. 결국 테스트 타깃에만 핵심 필드를 비교하는 `==` 를 손으로 쓰고 exhaustivity 를 껐습니다.

```swift
// 테스트 타깃에만 둡니다
extension EditorFeature.State: @retroactive Equatable {
  public static func == (lhs: Self, rhs: Self) -> Bool {
    lhs.items == rhs.items
  }
}

let store = TestStore(initialState: EditorFeature.State()) { EditorFeature() }
store.exhaustivity = .off
```

그렇게 하나둘 끄다 보니 지금은 TestStore 테스트 파일 122개 중 90개가 `exhaustivity = .off` 입니다.

exhaustivity 를 끄면 함정이 두 개 생깁니다.

- Effect 가 보낸 액션은 `receive` 나 `skipReceivedActions` 로 소비해야 `store.state` 에 반영됩니다. `finish()` 직후에 상태를 읽으면 옛 값이 보입니다.
- `send` 는 받아 두고 확인하지 않은 액션을 건너뜁니다. 순서를 바꿔 `send` 를 먼저 하면, 뒤의 `receive` 가 기다리다 실패합니다.

```swift
await store.send(.load)
await store.finish()
await store.skipReceivedActions(strict: false)   // 이게 없으면 옛 state 를 봅니다
#expect(store.state.items.count == 3)
```

`skipReceivedActions` 를 빼면 Effect 가 세 장을 다 불러왔는데도 `items.count` 가 0으로 보입니다.

![finish() 뒤 store.state 가 옛 값이라 실패한 테스트](/images/when-is-tca-2/when-is-tca-2-case4-finish.jpg)

**개선**

2.0 에서는 TestStore 가 Equatable 을 요구하지 않습니다(DebugSnapshots 로 비교). 손으로 쓴 `==` 를 지우고 exhaustive 테스트를 다시 켤 수 있습니다. 비동기 테스트도 덜 흔들리고 sleep · yield 도 거의 필요 없다고 합니다. 위 두 함정은 1.x TestStore 내부 동작이라 2.0 에서 사라질 수도 있지만, 직접 확인하지는 못했습니다.

### 5. delegate 액션의 파급

**문제**

자식 delegate 에 case 하나를 더하면, 다른 모듈에 있는 코디네이터의 switch 와 그 테스트가 같이 흔들립니다. 재현용 코드에서 delegate 에 `didShare` 하나만 더해도 코디네이터의 switch 가 바로 깨집니다.

![delegate 에 case 를 더하자 코디네이터 switch 에서 난 컴파일 에러](/images/when-is-tca-2/when-is-tca-2-case5-switch.jpg)

에이전트 여럿에게 작업을 나눠 줄 때는 「그 switch 는 누가 고치나」부터 정해야 했습니다.

**원인**

새기다는 기능 모듈끼리 서로 import 하지 않습니다. 화면 이동은 앱 코디네이터 리듀서가 맡고, 자식이 보낸 delegate 액션을 switch 해서 다음 화면을 정합니다.

delegate 액션은 [TCA 공식 튜토리얼](https://swiftpackageindex.com/pointfreeco/swift-composable-architecture/main/tutorials/composablearchitecture/02-01-yourfirstpresentation#Child-to-parent-communication)이 권하는 패턴입니다. 라이브러리가 따로 제공하는 기능은 아니고, 자식 Action 에 `case delegate(Delegate)` 를 직접 정의해서 씁니다.

![새기다 모듈 구조 — Feature 끼리는 import 하지 않고, App 의 코디네이터가 delegate 를 받아 화면을 잇습니다](/images/when-is-tca-2/when-is-tca-2-architecture.svg)

delegate enum 이 39개, 코디네이터가 delegate 를 받는 줄이 60줄쯤 됩니다. delegate 는 자식의 공개 Action 이라, case 가 늘 때마다 그걸 switch 하는 코디네이터도 같이 고쳐야 합니다.

```swift
// 1.x — 자식
enum Action {
  case delegate(Delegate)
  enum Delegate { case didSave(Note), didClose }
}

// 1.x — 부모(코디네이터)
case let .editor(.delegate(.didSave(note))):
  state.path.append(.detail(DetailFeature.State(note: note)))
  return .none
```

**개선**

2.0 은 delegate 액션 대신 delegate 클로저를 권합니다. 자식은 init 에서 클로저를 받고, 부모가 scope 할 때 넘겨줍니다. 위로 올려 보내는 event 도 있어서 조상이 `.onEvent` 로 받을 수 있습니다. 공개 Action 이 덜 불어나니, case 하나가 여러 모듈로 번지는 일도 줄 것 같습니다.

다만 아직 모르는 게 하나 있습니다. 2.0 으로 옮긴 Feature 와 1.x 에 남은 Feature 가 코디네이터를 거쳐 대화할 수 있는지가 글에 나오지 않습니다. 새기다는 코디네이터가 모든 화면을 잇는 구조라, 여기서 막히면 Feature 를 하나씩 옮기는 방식이 막힙니다.

### 6. 다시 불리는 onAppear 와 시작 플래그

**문제**

탭을 오가거나 분할 화면의 열이 다시 나타날 때마다 시작 작업이 또 돌았습니다.

**원인**

`onAppear` 는 화면이 다시 보일 때마다 불립니다. 그래서 「이미 시작했나」 플래그를 달았고, 이런 플래그가 열두 개쯤 됩니다.

```swift
case .onAppear:
  guard !state.didStart else { return .none }
  state.didStart = true
  return .run { send in /* 처음 한 번만 */ }
```

**개선**

2.0 에서는 `.onMount` 가 상태가 생길 때 한 번만 돕니다. 화면이 다시 보인다고 다시 돌지 않으니, 이런 플래그를 지울 수 있습니다.

## 2.0 으로 기대하는 장점

여섯 가지를 묶어 보면, 2.0 으로 옮겼을 때 기대하는 장점은 다섯 가지입니다.

- **정리와 시작이 뷰가 아닌 상태의 생명주기를 따라갑니다.** `.onMount` · `.onDismount` 가 상태가 생기고 없어질 때 불립니다. 늦게 도착하는 정리 액션도, 다시 시작을 막는 플래그도 필요 없어집니다. (1번 · 6번, 생명주기 개선)
- **규칙으로 막던 버그를 구조가 막아 줍니다.** `Update` 가 아무것도 돌려주지 않으니 `return .none` 이 nil 로 읽히는 버그는 생길 수 없습니다. (2번, Effect 반환 개선)
- **비동기 결과를 다루는 판단이 한곳에 모입니다.** 작업 안에서 지금 상태를 읽고 바로 씁니다. 캡처 리스트와 응답 액션으로 나뉘던 판단을 한 블록에서 끝낼 수 있습니다. (3번, 비동기 상태 갱신 개선)
- **테스트를 다시 엄격하게 돌릴 수 있습니다.** TestStore 가 Equatable 을 요구하지 않아서, 손으로 쓴 `==` 를 지우고 exhaustive 테스트를 다시 켤 수 있습니다. (4번, TestStore 개선)
- **모듈 사이의 파급이 줄어듭니다.** delegate 클로저와 event 를 쓰면 공개 Action 이 덜 불어납니다. case 하나가 다른 모듈의 switch 를 깨는 일이 줄고, 여러 에이전트에게 작업을 나눠 줄 때 「그 switch 는 누가 고치나」를 정할 일도 줄 것 같습니다. (5번, delegate 개선)

## 그래서 얼마나 바꿔야 하나요

어떻게 올리느냐에 따라 다릅니다. 아래 수치는 Claude Code 를 돌려 저장소를 grep 으로 센 근사치(주석 포함)입니다.

**버전만 올리고 1.x 코드를 그대로 두면: 할 만합니다.** 옛 API(`ViewStore`, `WithViewStore`, `TaskResult`)와 1.25 의 hard deprecation 은 이미 0곳입니다. trait 으로 켜는 deprecation 경고는 56곳쯤 예상합니다. 걱정되는 건 두 가지입니다.

- `ComposableArchitecture1` 로 둔 코드도 속은 2.0 런타임에서 돌아서, Effect 실행 순서가 바뀌면 테스트가 깨질 수 있습니다.
- 「대부분 타입이 Sendable 아님」이 Swift 6 언어 모드에서는 경고가 아니라 컴파일 오류로 올 수 있습니다.

**2.0 방식으로 다시 쓰면: 큰 공사입니다.** 2.0 이 가장 크게 바꾸는 두 가지가 새기다 코드의 뼈대와 그대로 겹칩니다.

| 무엇                                  | 개수            |
| ----------------------------------- | ------------- |
| `@Reducer`                          | 81            |
| `Effect<Action>` 을 돌려주는 헬퍼 함수       | 499           |
| `return .none`                      | 1,038         |
| delegate enum / 부모가 delegate 를 받는 곳 | 39 / 68       |
| 테스트의 `send` / `receive`             | 2,880 / 1,856 |

## 결론: 기다렸다가, 하나씩

올릴 계획이고, 순서는 이렇게 잡았습니다.

1. 2.0.0 이 나오자마자 올리지는 않습니다. 「근본적인 재설계」라서 패치가 몇 번 나와 안정되기를 기다립니다. 지금 하고 있는 3.0(iPhone 지원)도 끝낸 뒤에 합니다.
2. 먼저 버전만 올리고, 기존 코드는 `ComposableArchitecture1` 로 그대로 둔 채 전체 회귀 테스트로 확인합니다.
3. 그다음 **손댈 일이 생긴 Feature 부터** 2.0 으로 옮깁니다. 2 · 3번이 걸린 필사 편집 화면, 1번이 걸린 광고 갱신과 설정 하위 화면이 1순위입니다.
4. 거의 안 건드리는 화면은 1.x 코드 그대로 둡니다.

이렇게 나눈 이유는, 위의 개선 대부분이 버전만 올려서는 생기지 않기 때문입니다. 그 Feature 를 2.0 방식으로 옮겨야 생깁니다.

결정 전에 확인할 것도 셋 남겨 뒀습니다. 2.0 의 최소 OS(새기다는 iOS 17), 네비게이션과 `@Shared` · `@Dependency` 의 변화, 그리고 5번에서 말한 1.x 에 남은 Feature 와의 대화입니다.

지금 1.x 에서 할 수 있는 준비도 있습니다. 1.25 부터 있는 trait 을 켜면 2.0 에서 사라질 API 에 미리 경고가 뜹니다.

```swift
// Package.swift
.package(
  url: "https://github.com/pointfreeco/swift-composable-architecture",
  from: "1.25.0",
  traits: ["ComposableArchitecture2Deprecations"]
)
```

단, trait 문법은 `swift-tools-version` 6.1 이상에서만 씁니다. 새기다는 아직 6.0 이고 Tuist 가 trait 을 넘겨주는지도 확인해야 해서, 이 측정은 아직 하지 않았습니다.
