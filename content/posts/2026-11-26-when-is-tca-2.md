Point-Free 의 블랙프라이데이 할인 메일을 읽다가 「내년에 다룰 것」 목록에 ComposableArchitecture 2.0 이 들어 있는 걸 봤습니다.

![Point-Free 블랙프라이데이 공지 — 내년 계획에 ComposableArchitecture 2.0 이 적혀 있습니다](/images/when-is-tca-2/when-is-tca-2-1.png)

엄밀히는 출시 예고가 아니라 「내년에 다룰 주제」 목록이에요. 그래도 내년에 본격적으로 다룬다니, 미리 따져 보기로 했습니다.

새기다(Carve)는 Apple Pencil 로 성경을 필사하는 앱이고 처음부터 TCA 로 만들었습니다. 혼자 만드는 앱이라 마이그레이션 비용은 고스란히 제 몫입니다.

먼저 결론입니다.

- **언제 나오는지는 아직 모릅니다.** 출시일은 발표되지 않았습니다.
- 대신 미리보기 문서를 읽어 보니, **2.0 이 바꾸는 곳이 새기다에서 겪은 문제와 거의 겹쳤습니다.**
- 그래서 올립니다. 다만 나오자마자가 아니라, 안정되면 호환층으로 먼저 올리고 손대는 화면부터 하나씩 옮깁니다.

## 그래서 언제 나오나요

2026-11-26 기준으로 아는 건 이게 전부입니다.

- 2026-03 에 나온 1.25 가 2.0 대비 폐기(deprecation)를 한 묶음 넣었습니다. 일부는 바로 경고가 나고 일부는 SwiftPM 트레잇을 켜야 납니다.
- 2026-04-01 에 2.0 베타 미리보기가 공개됐습니다. 유료 회원(Point-Free Max) 전용입니다.
- 공개 저장소 최신은 1.26.2(2026-08)이고 2.0 태그는 없습니다.

그래서 「언제」 대신 「무엇이 바뀌는지」를 봤습니다.

## 2.0 에서 바뀌는 것

미리보기 글에서 큰 것만 추렸습니다. 베타를 직접 만져 보진 않았으니 전부 글에 적힌 내용 기준입니다.

| 영역 | 1.x | 2.0 |
|---|---|---|
| Feature 정의 | `@Reducer`, `Reduce { ... return effect }` | `@Feature`, `Update { }` — 동기이고 아무것도 돌려주지 않음 |
| 부수 효과 | `Effect` 를 돌려줌(`.run`, `.send`, `.merge`) | `store.addTask { }`. 작업 안에서 상태를 읽고 `store.modify` 로 씀 |
| 생명 주기 | 뷰의 `onAppear` · `onDisappear` 에서 액션 보내기 | `.onMount` · `.onDismount`. onMount 에서 시작한 작업은 상태가 없어질 때 자동 취소 |
| 부모와 자식 | delegate 액션을 부모가 switch | delegate 클로저, preference, event, trigger |
| 바인딩 | `BindableAction` + `BindingReducer` | `@Bindable` 하나면 됨 |
| 시험 | `TestStore` 가 `State: Equatable` 을 요구 | 여전히 철저(exhaustive) 시험, Equatable 은 필요 없음 |
| 동시성 | — | Store 가 기본 `@MainActor`. 라이브러리 타입 대부분이 더는 Sendable 이 아님 |

제일 반가운 건 호환층입니다. 2.0 패키지에 `ComposableArchitecture1` 이 같이 들어 있어서 `import ComposableArchitecture` 를 그대로 두면 1.x 코드가 컴파일된다고 합니다. 옮기고 싶은 Feature 만 `ComposableArchitecture2` 로 import 를 바꾸면 됩니다. 한 번에 다 갈아엎지 않아도 돼요.

## 겪은 문제 여섯 가지

새기다를 만들며 TCA 때문에 시간을 쓴 일 여섯 가지를 골랐습니다. 예제 코드는 설명용으로 새로 썼고 2.0 코드는 미리보기 글을 보고 그린 모양이라 실제 API 와 다를 수 있습니다. 스크린숏은 이 글을 위해 따로 만든 재현용 앱에서 찍었습니다.

### 1. 늦은 onDisappear 경고

설정 하위 화면을 닫을 때마다 TCA 가 경고를 냈습니다. 자식 상태는 이미 nil 인데 `ifLet` 에 자식 액션이 도착했다는 내용이었습니다.

순서 문제였어요. 화면을 닫으면 부모 리듀서가 먼저 자식 상태를 nil 로 바꾸고 SwiftUI 는 그 **다음에** `onDisappear` 를 부릅니다. 그래서 정리하려고 보낸 액션이 받을 상태가 없을 때 도착합니다.

```swift
// 1.x — 닫을 때마다 경고가 납니다
SyncStatusView(store: store)
  .onDisappear { store.send(.stopObserving) }
```

재현용 앱에서 시트를 「완료」로 닫으면, Xcode 가 TCA 안쪽에 보라색 runtime warning 을 띄웁니다. 경고 문구는 *received a presentation action when destination state was absent* 입니다.

![시트를 닫은 뒤 ifLet 이 nil 상태에서 액션을 받았다는 Xcode runtime warning](/images/when-is-tca-2/when-is-tca-2-case1-ondisappear.jpg)

그래서 지금은 「띄운 화면은 onDisappear 로 액션을 보내지 않는다」를 규칙으로 두고 있습니다. `ifLet` · `@Presents` 로 띄운 화면의 효과는 부모가 상태를 치우는 순간 TCA 가 알아서 취소해 주니까요. 뷰 수명에 꼭 묶어야 하는 일만 `.task` 에 묶습니다.

```swift
// 1.x — 뷰가 사라지면 .task 가 취소되고, 그 안의 효과도 함께 끝납니다
SyncStatusView(store: store)
  .task { await store.send(.task).finish() }
```

**2.0 에서는** 정리가 화면이 아니라 **상태 수명**을 따라갑니다. `.onMount` 에서 시작한 작업은 상태가 없어질 때 취소되고 `.onDismount` 는 상태가 없어지는 그 순간 불립니다. 늦게 도착할 액션이 애초에 없습니다.

```swift
// 2.0 미리보기를 보고 그린 모양 — 실제 API 와 다를 수 있습니다
var body: some Feature {
  Update { state, action in
    // 상태만 바꿉니다
  }
  .onMount { state in
    store.addTask {
      for await status in syncClient.statusUpdates() {
        try store.modify { $0.status = status }
      }
    }
  }
}
```

다만 상태는 남고 화면만 가려지는 경우는 여전히 뷰의 몫입니다. iPhone 에서 탭을 오갈 때나, 보일 때만 돌아야 하는 광고 갱신 타이머가 그렇습니다. `onDismount` 는 「상태가 없어질 때」지 「안 보일 때」가 아니니까요.

### 2. `Effect?` 도우미의 `return .none` 이 nil 이 됨

리듀서가 커지면 주제별 도우미 함수로 나눴습니다. 도우미는 `Effect<Action>?` 를 돌려주고 nil 이면 「내 담당 아님, 다음 도우미로」라는 약속이었습니다.

그런데 필사 화면에서 늦게 도착한 조회 결과를 버려야 하는 갈래가 조용히 무시됐습니다. 다음 도우미가 그 결과를 화면에 합쳐 버렸고 이 결함은 2.0 판부터 몇 달 동안 나간 모든 출시판에 들어 있었습니다.

원인은 `return .none` 이었습니다. 반환 타입이 `Effect<Action>?` 이면 Swift 는 `.none` 을 TCA 의 `Effect.none` 이 아니라 `Optional.none`, 즉 nil 로 읽습니다. 그런데 컴파일러는 끝까지 아무 말도 안 해요.

```swift
func reduceLoading(_ action: Action, state: inout State) -> Effect<Action>? {
  switch action {
  case let .loaded(result):
    guard !state.isClosing else {
      return .none   // 의도: 「처리 끝, 효과 없음」  실제: nil 「내 담당 아님」
    }
    state.content = result
    return .none     // 여기도 nil 이지만, 이미 처리를 마쳐서 결과가 같았습니다
  default:
    return nil
  }
}

// body
if let effect = reduceLoading(action, state: &state) { return effect }
return reduceOther(action, state: &state)   // 버렸어야 할 결과가 여기로 넘어갑니다
```

빌드는 경고 0으로 지나가고, 철저 시험을 돌려야 「바뀌면 안 되는 상태가 바뀌었다」로 드러납니다.

![닫는 중에 도착한 결과를 버려야 하는데 상태가 바뀌어 실패한 시험](/images/when-is-tca-2/when-is-tca-2-case2-nil.jpg)

고치는 건 한 줄이었습니다. `return Effect<Action>.none` 으로 타입을 적으면 돼요. 같은 모양이 여섯 군데 더 있었는데, 다행히 거기서는 뒤 갈래도 아무것도 하지 않아 결과가 같았습니다.

**2.0 에서는** `Update` 가 아무것도 돌려주지 않습니다. 「효과 없음」과 「내 담당 아님」을 같은 단어로 쓸 일 자체가 없으니, 이런 결함은 생길 수가 없습니다. 지금은 규칙으로 막는 걸 2.0 은 구조로 막아 줍니다.

### 3. 효과의 값 캡처와 응답 액션

지금은 효과가 출발할 때 필요한 값을 캡처해 가고 결과는 응답 액션으로 돌아와 리듀서가 상태에 씁니다. 새기다에는 이런 캡처 목록이 170곳쯤 있습니다.

```swift
// 1.x
case .refresh:
  return .run { [id = state.chapterID] send in
    let page = try await client.fetch(id)
    await send(.fetched(page))
  }

case let .fetched(page):
  guard page.id == state.chapterID else { return .none }   // 그사이 바뀌었으면 버립니다
  state.page = page
  return .none
```

캡처한 값은 출발할 때의 값입니다. 결과가 늦게 도착하면 「아직 그 장이 열려 있나」를 응답 액션에서 다시 확인해야 합니다. 2번의 「버리는 갈래」도 이렇게 생겼습니다. 판단이 두 군데로 흩어지는 거죠.

**2.0 에서는** 작업 안에서 지금 상태를 읽고 `store.modify` 로 바로 씁니다. 응답 액션도, 흩어진 판단도 사라집니다.

```swift
// 2.0 미리보기를 보고 그린 모양
case .refresh:
  store.addTask {
    let id = try store.chapterID
    let page = try await client.fetch(id)
    try store.modify { state in
      guard state.chapterID == id else { return }
      state.page = page
    }
  }
```

### 4. TestStore 가 요구하는 `State: Equatable`

빌드 경고를 정리하다가 리듀서를 직접 부르던 시험(1.x 에서 폐기 경고가 나는 방식)을 `TestStore` 로 옮겼습니다. 그런데 TestStore 는 `State: Equatable` 을 요구하고 몇몇 State 는 Equatable 로 만들기 어려운 값을 들고 있었습니다. Equatable 이 아닌 State 로 시험을 만들면 그 줄에서 바로 컴파일 에러가 납니다.

![TestStore 가 State 의 Equatable 을 요구하는 컴파일 에러](/images/when-is-tca-2/when-is-tca-2-case4-equatable.jpg)

결국 시험 타깃에만 핵심 필드를 비교하는 `==` 를 손으로 쓰고 철저 시험은 껐습니다.

```swift
// 시험 타깃에만 둡니다
extension EditorFeature.State: @retroactive Equatable {
  public static func == (lhs: Self, rhs: Self) -> Bool {
    lhs.items == rhs.items
  }
}

let store = TestStore(initialState: EditorFeature.State()) { EditorFeature() }
store.exhaustivity = .off
```

그렇게 하나둘 끄다 보니 지금은 TestStore 시험 파일 122개 중 90개가 `exhaustivity = .off` 입니다.

철저 시험을 끄면 함정이 두 개 생깁니다.

- 효과가 보낸 액션은 `receive` 나 `skipReceivedActions` 로 소비해야 `store.state` 에 반영됩니다. `finish()` 직후에 상태를 읽으면 옛 값이 보입니다.
- `send` 는 받아 두고 확인하지 않은 액션을 건너뜁니다. 순서를 바꿔 `send` 를 먼저 하면, 뒤의 `receive` 가 기다리다 실패합니다.

```swift
await store.send(.load)
await store.finish()
await store.skipReceivedActions(strict: false)   // 이게 없으면 옛 state 를 봅니다
#expect(store.state.items.count == 3)
```

`skipReceivedActions` 를 빼면 효과가 세 장을 다 불러왔는데도 `items.count` 가 0으로 보입니다.

![finish() 뒤 store.state 가 옛 값이라 실패한 시험](/images/when-is-tca-2/when-is-tca-2-case4-finish.jpg)

**2.0 에서는** TestStore 가 Equatable 을 요구하지 않습니다(DebugSnapshots 로 비교). 손으로 쓴 `==` 를 지우고 철저 시험을 다시 켤 수 있습니다. 비동기 시험도 덜 흔들리고 sleep · yield 도 거의 필요 없다고 합니다. 위 두 함정은 1.x TestStore 내부 동작이라 2.0 에서 사라질 수도 있지만 직접 확인하지는 못했어요.

### 5. delegate 액션의 파급

새기다는 기능 모듈끼리 서로 import 하지 않습니다. 화면 이동은 앱 코디네이터 리듀서가 맡고 자식이 보낸 delegate 액션을 switch 해서 다음 화면을 정합니다. delegate enum 이 39개, 코디네이터가 delegate 를 받는 줄이 60줄쯤 됩니다.

```swift
// 1.x — 자식
enum Action {
  case delegate(Delegate)
  enum Delegate { case didSave(Note), didClose }
}

// 1.x — 부모(코디네이터)
case let .editor(.delegate(.didSave(note))):
  state.path.append(.detail(DetailFeature.State(note: note)))
  return .none
```

자식 delegate 에 case 하나를 더하면, 다른 모듈에 있는 코디네이터의 switch 와 그 시험이 같이 흔들립니다. 에이전트 여럿에게 작업을 나눠 줄 때는 「그 switch 는 누가 고치나」부터 정해야 했어요.

재현용 코드에서 delegate 에 `didShare` 하나만 더해도 코디네이터의 switch 가 바로 깨집니다.

![delegate 에 case 를 더하자 코디네이터 switch 에서 난 컴파일 에러](/images/when-is-tca-2/when-is-tca-2-case5-switch.jpg)

**2.0 에서는** delegate 액션이 없어집니다. 자식은 init 에서 클로저를 받고 부모가 scope 할 때 넘겨줍니다. 위로 올려 보내는 event 도 있어서 조상이 `.onEvent` 로 받을 수 있습니다. 공개 Action 이 덜 불어나니, case 하나가 여러 모듈로 번지는 일도 줄 것 같습니다.

다만 아직 모르는 게 하나 있습니다. 2.0 으로 옮긴 Feature 와 호환층에 남은 Feature 가 코디네이터를 거쳐 대화할 수 있는지가 글에 나오지 않아요. 새기다는 코디네이터가 모든 화면을 잇는 구조라 여기서 막히면 Feature 를 하나씩 옮기는 방식이 막힙니다.

### 6. 다시 불리는 onAppear 와 시작 플래그

탭을 오가거나 분할 화면의 열이 다시 나타나면 `onAppear` 가 또 불립니다. 그때마다 시작 작업도 다시 돌았습니다. 그래서 「이미 시작했나」 플래그를 달았고 이런 플래그가 열두 개쯤 됩니다.

```swift
case .onAppear:
  guard !state.didStart else { return .none }
  state.didStart = true
  return .run { send in /* 처음 한 번만 */ }
```

**2.0 에서는** `.onMount` 가 상태가 생길 때 한 번만 돕니다. 화면이 다시 보인다고 다시 돌지 않으니, 이런 플래그를 지울 수 있습니다.

## 그래서 얼마나 바꿔야 하나요

어떻게 올리느냐에 따라 달라요. 아래는 grep 으로 센 근사치(주석 포함)입니다.

**호환층으로 버전만 올리면: 할 만합니다.** 옛 API(`ViewStore`, `WithViewStore`, `TaskResult`)와 1.25 의 강한 폐기는 이미 0곳입니다. 트레잇 폐기 경고는 56곳쯤 예상합니다. 걱정되는 건 두 가지예요.

- 호환층도 속은 2.0 런타임이라 효과 실행 순서가 바뀌면 시험이 깨질 수 있습니다.
- 「대부분 타입이 Sendable 아님」이 Swift 6 언어 모드에서는 경고가 아니라 컴파일 오류로 올 수 있습니다.

**2.0 방식으로 다시 쓰면: 큰 공사입니다.** 2.0 이 가장 크게 바꾸는 두 가지가 새기다 코드의 뼈대와 그대로 겹칩니다.

| 무엇 | 개수 |
|---|---|
| `@Reducer` | 81 |
| `Effect<Action>` 을 돌려주는 도우미 함수 | 499 |
| `return .none` | 1,038 |
| delegate enum / 부모가 delegate 를 받는 곳 | 39 / 68 |
| 시험의 `send` / `receive` | 2,880 / 1,856 |

## 결론: 기다렸다가, 하나씩

올리기로 했습니다. 순서는 이렇게 정했습니다.

1. 2.0.0 이 나오자마자는 안 합니다. 「근본적인 재설계」라서 패치가 몇 번 나와 안정되기를 기다립니다. 지금 하고 있는 3.0(iPhone 지원)도 끝낸 뒤에 합니다.
2. 먼저 호환층으로 버전만 올리고 전체 회귀로 확인합니다.
3. 그다음 **손댈 일이 생긴 Feature 부터** 2.0 으로 옮깁니다. 2 · 3번이 걸린 필사 편집 화면, 1번이 걸린 광고 갱신과 설정 하위 화면이 1순위입니다.
4. 거의 안 건드리는 화면은 호환층에 그대로 둡니다.

결정 전에 확인할 것도 셋 남겨 뒀습니다. 2.0 의 최소 OS(새기다는 iOS 17), 내비게이션과 `@Shared` · `@Dependency` 의 변화, 그리고 5번에서 말한 호환층 Feature 와의 대화입니다.

지금 1.x 에서 할 수 있는 준비도 있습니다. 1.25 부터 있는 트레잇을 켜면 2.0 에서 사라질 API 에 미리 경고가 뜹니다.

```swift
// Package.swift
.package(
  url: "https://github.com/pointfreeco/swift-composable-architecture",
  from: "1.25.0",
  traits: ["ComposableArchitecture2Deprecations"]
)
```

단, 트레잇 문법은 `swift-tools-version` 6.1 이상에서만 씁니다. 새기다는 아직 6.0 이고 Tuist 가 트레잇을 넘겨주는지도 확인해야 해서 이 측정은 아직 하지 않았습니다.

## 시행착오

- 처음엔 「send 2,880번이 순서 변화로 깨질 수 있다」고 위험을 크게 잡았습니다. 다시 보니 시험 파일 4개 중 3개가 이미 철저 시험을 꺼 둔 상태라 생각보다 덜 민감했습니다. 4번의 우회가 여기서는 위험을 줄인 셈입니다.
- 위의 이점 대부분은 **호환층으로 올리기만 해서는 생기지 않습니다.** 그 Feature 를 2.0 방식으로 옮겨야 생깁니다. 버전만 올리고 「onDisappear 경고도 사라졌겠지」 기대하면 안 됩니다.
- 2.0 내용은 전부 미리보기 기준이라 정식판에서 달라질 수 있습니다.
- 2.0 이 풀어 주지 않는 문제도 있습니다. 공유 저장소 초기화 순서에 따라 실패하는 시험, PencilKit 쪽 디바운스 시험은 TCA 밖의 일입니다.
